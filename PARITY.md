# Parity audit vs. Python `mlx_whisper`

**Reference:** `mlx-whisper` **0.4.3** (PyPI), the version pinned in
`tests/fixtures/manifest.json`.
**Method:** line-by-line comparison of each Rust module against its Python
counterpart, plus golden fixtures generated by running the real Python
implementation (`tools/gen_fixtures.py`).

Severity key:

| | meaning |
|---|---|
| **BUG** | produces wrong output or crashes |
| RISK | diverges; may be benign, but can bite |
| DOC | documentation or asset mismatch only |
| OK-DIFF | deliberate, acceptable difference |

> **Verification status.** The audit itself was done on Linux, where this
> crate cannot build (`mlx-sys` links Foundation/objc/Metal/Accelerate
> unconditionally). The *Python* side was executed for real throughout — MLX
> ships Linux CPU wheels — so every fixture and every claim marked "measured"
> comes from running upstream `mlx_whisper` 0.4.3. The Rust side is now built
> and tested on macOS arm64 in CI (`.github/workflows/ci.yml`).
>
> Note that CI pins MLX to the **CPU** device via `MLX_WHISPER_RS_TEST_CPU`.
> GitHub's macOS runners are VMs with paravirtualised Metal, and MLX GPU work
> aborts there with an `AppleParavirtCommandBuffer` assertion — a SIGABRT that
> kills the whole test binary. The GPU path is therefore **not** covered by CI
> and still needs a real Mac.

## `audio.rs`

### AUDIO-1 — STFT reflect padding is silently dropped — **BUG** (measured)

`src/audio.rs:121-125`:

```rust
let prefix = x.index(1..(padding + 1));
let prefix = prefix.index((..prefix.shape()[0]).stride_by(-1));   // <-- empty
```

`mlx-rs` resolves a bounded range with a negative stride as
`start = size - 1, end = n` (`mlx-rs-0.25.3/src/ops/indexing/mod.rs:179-223`:
an unbounded start with `stride < 0` becomes `size - 1`). For `n == size` that
is Python `x[:200:-1]` — an **empty** slice. The idiom that means `x[::-1]` is
`(..).stride_by(-1)`, with the range left unbounded.

Measured in real MLX:

```
x[:200:-1] shape  -> (0,)     # what the current code produces
x[::-1]    shape  -> (200,)   # what it intended
```

Consequence: no padding is applied, so every frame is shifted by `N_FFT/2 = 200`
samples and a 30 s chunk yields **2997 frames instead of 3000** (measured). The
encoder is fed a mis-aligned, short spectrogram on every transcription.

**Fix:** drop the bound — `prefix.index((..).stride_by(-1))`, and likewise for
`suffix`.

**Test:** `tests/audio_parity.rs::log_mel_full_chunk_yields_exactly_n_frames`,
`::log_mel_produces_the_upstream_frame_count`, `::log_mel_matches_upstream_values`.

### AUDIO-2 — `log_mel_spectrogram` has no `padding` parameter — **BUG**

Python `audio.py:132-136` takes `padding: int = 0` and appends that many zero
**samples** before the STFT; `transcribe.py:150` calls it with
`padding=N_SAMPLES`. The Rust signature (`src/audio.rs:147`) has no such
parameter and `src/transcribe.rs:250` cannot pass one.

Frame accounting still agrees, so segmentation and timestamps are unaffected.
The transcription loop is unaffected too: upstream slices
`mel[seek : seek + segment_size]` with `segment_size = min(N_FRAMES,
content_frames - seek)`, which never reaches the padded region, and then
zero-pads to `N_FRAMES` exactly as this port does (`transcribe.py:289-294`).

What the padding *does* change is `detect_language`: upstream feeds
`pad_or_trim(mel, N_FRAMES)` over the **padded** mel (`transcribe.py:172`), so
for clips under 30s the tail is real mel-of-silence rather than `0.0` in
normalised log space. It also shifts the global `log_spec.max()` used for
normalisation. Language ID therefore sees a different encoder input on any
short clip.

**Fix:** add `padding: usize` to `log_mel_spectrogram`, pass `N_SAMPLES` from
`transcribe`, set `content_frames = mel.shape[0] - N_FRAMES`, and take the
language-ID slice from the padded mel. This is a public API change.

### AUDIO-3 — `audio_from_wav_bytes` panics on a truncated `fmt ` chunk — **BUG**

`src/audio.rs:216-222` validates only the *declared* `chunk_size >= 16`; the
loop guard is `pos + 8 <= bytes.len()`. `u16le(data_off + 14)` then reads
`bytes[pos+22..pos+24]` unchecked. A truncated or malformed WAV panics with an
index-out-of-bounds instead of returning `Err` from a `Result`-returning parser
fed untrusted bytes.

**Test:** `tests/wav_parsing.rs::rejects_truncated_fmt_chunk_without_panicking`,
`::rejects_truncated_header_prefixes`.

### AUDIO-4 — mel filterbank asset format mismatch — **DOC** (measured)

Upstream ships a **single** `assets/mel_filters.npz` (keys `mel_80`, `mel_128`);
`src/audio.rs:89` reads separate `mel_filters_{n}.npy`. The README's
`cp "$MLXW/assets/"*.npy assets/` therefore matches **nothing**, and
`mel_filters()` fails at runtime for anyone following the documented setup.

**Fixed** in this change: `tools/extract_assets.py` unpacks the npz into the
expected layout (verified byte-identical to the committed fixtures), and the
README now points at it.

### AUDIO-5 — the `.npy` reader validates nothing — RISK

`src/audio.rs:94-113` never parses the header dict: `descr` (dtype),
`fortran_order`, and `shape` are all ignored, and only npy **v1.0** framing is
handled. A `fortran_order: True` file has an identical byte count, passes
`Array::from_slice`'s length assert, and yields **silently transposed** filters.
`<f8` or a truncated file panics. Files under 6 bytes panic at `bytes[..6]`.

### AUDIO-6 — `WAVE_FORMAT_EXTENSIBLE` and 24-bit rejected — RISK

`src/audio.rs:239-255` matches only `(1,16)`, `(1,32)`, `(3,32)`. Format
`0xFFFE` (EXTENSIBLE — common for multichannel and 24-bit recorders, with the
real format in the `SubFormat` GUID) is rejected even when the payload is
ordinary 16-bit PCM. Fails cleanly, but rejects valid input.

### AUDIO-7 — WAV sample rate never enforced — RISK

`audio_from_wav_bytes` returns `(Array, u32)` and defers rate validation to the
caller — but **nothing in `src/` calls it**, so the contract is entirely
unenforced. A 44.1 kHz file silently produces a spectrogram with a ~2.76×
wrong time base. `sample_rate == 0` is not rejected either.

### AUDIO-8 — `stft` frame count underflows — RISK

`src/audio.rs:130`: `(x.size() - nperseg + noverlap) / noverlap` in `usize`. For
inputs under 240 samples this panics in debug and **wraps to ~1.8e19** in
release, which is then handed to `as_strided`. After AUDIO-1 is fixed the
reflect pad guarantees `size >= n + 400`, so it only matters for degenerate
input — but it should return `Err`.

### AUDIO-9 — `mel_filters()` panics on an unsupported `n_mels` — **BUG**

`src/audio.rs:87` (`mel_filters`) validated `n_mels` with `assert!(n_mels ==
80 || n_mels == 128, ...)` inside a `Result`-returning function. `n_mels`
comes from a downloaded model's `config.json` via `model.dims.n_mels`, so a
repo declaring e.g. `n_mels: 64` panicked and unwound through the library
boundary instead of returning `Err`, the same contract every sibling
validation in this file already follows.

**Fixed** in this change: the `assert!` is now `bail!("n_mels must be 80 or
128, got {n_mels} (from the model's config.json)")` (`src/audio.rs:92`).

### OK-DIFF

`load_audio` has no stdin mode; `pad_or_trim` hardcodes axis 0 (correct for
every real call site); no `lru_cache` on the filterbank or Hann window
(re-read from disk per call — performance only); `log_mel_spectrogram` accepts
only `Array`, not a path.

**Verified matching:** all nine constants; the periodic Hann identity;
`nperseg`/`noverlap`/`nfft` and the `as_strided` shape, strides and offset; the
last-frame drop; `abs().square()` (magnitude *squared*); `rfft` defaults;
`filters.T` orientation and matmul order; the `1e-10` clamp, the **global**
`max() - 8.0` floor, and `(x + 4) / 4`; `audio_from_pcm_s16le` scaling; WAV
word alignment and multi-channel mean downmix.

## `decoding.rs`

### DEC-1 — the final timestamp rule normalises the wrong logits — **BUG**

`src/decoding.rs:169-179` computes

```rust
let logprobs = &logits_masked - &logsumexp_axis(&logits_masked, 0, true)?;
```

Python (`decoding.py:383-394`) normalises the **unmasked** input logits — the
ones carrying only `SuppressBlank`/`SuppressTokens`, *not* this filter's own
mask. Two consequences:

* In the "two consecutive timestamps → next must be text" branch the whole
  `[ts_begin..]` range is already `-inf` in Rust, so `ts_lp == -inf` and the
  text-suppression clause **can never fire**. Python evaluates it on unmasked
  logits and can fire.
* The two normalisations use different denominators, so the
  `ts_lp > max_text_lp` comparison can flip at ordinary steps.

The log-space/`logsumexp` formulation itself is correct; the *input* is wrong.

### DEC-2 — timestamp monotonicity: this port is *more* correct than upstream — **BUG (upstream)** (measured)

`mlx_whisper` 0.4.3 collects list **indices** where `openai/whisper` collects
token **values**:

```python
# openai/whisper — values, >=
timestamps = sampled_tokens[sampled_tokens.ge(tokenizer.timestamp_begin)]

# mlx_whisper 0.4.3 — indices, strict >
timestamps = [i for i, v in enumerate(seq) if v > tokenizer.timestamp_begin]
```

`last_timestamp` is then a position inside `seq` — a small integer far below
`timestamp_begin` (50364) — so the mask range `[timestamp_begin :
last_timestamp]` is **empty** and the "timestamps shouldn't decrease"
constraint never fires. Upstream also tests the numeric `last_timestamp`
where openai tests the boolean `last_was_timestamp`.

Measured on the committed cases (count of `-inf` entries, `text_dominant` row):

| case | mlx_whisper | openai/whisper |
|---|---:|---:|
| `monotonic` | 1 | 32 |
| `zero_timestamp` | 1 | 2 |
| `after_paired_timestamps` | 50258 | 50288 |

`src/decoding.rs:141-153` collects **values** and uses `!last_was_timestamp ||
penultimate_was_timestamp` — i.e. it follows **openai/whisper** and actively
enforces monotonicity. It used `>` rather than openai's `>=`, so `<|0.00|>`
never entered the list, leaving the clause inert for a sequence like
`[<|0.00|>, "hello"]`.

**Fixed** in this change: the filter now reads `t >= ts_begin`, matching
openai's `sampled_tokens.ge(tokenizer.timestamp_begin)`.

**This is a decision, not a defect to fix blindly.** Strict parity with
`mlx_whisper` would mean reproducing an upstream bug. The fixture now carries
**three** expectation sets in `tests/fixtures/logit_filters.json`:
`timestamp_rules` (mlx_whisper), `timestamp_rules_openai_semantics`
(openai/whisper), and `timestamp_rules_port_semantics` — this port's actual
hybrid behaviour, mlx_whisper's unmasked `DEC-1` normalisation combined with
openai's `>=` monotonicity clause here, which neither of the first two sets
describes. `timestamp_rules_port_semantics` is generated by the new
`tools/reference_rules.py` and is the set the suite asserts against
(`decoding::tests::timestamp_rules_match_the_port_semantics_fixture`); the
decision itself is still pinned separately by
`decoding::tests::timestamp_rules_enforce_monotonic_timestamps`. See
`tests/fixtures/README.md`.

### DEC-3 — `-1` combined with explicit suppress ids — RISK

`src/decoding.rs:291-295`: when `-1` is present, Rust extends with
`non_speech_tokens` **only**, discarding co-listed explicit ids (the `else`
branch is unreachable). Python keeps all `t >= 0` *and* adds the non-speech set,
so `"-1,50257"` suppresses 50257 upstream but not here. Benign for the default
`"-1"`.

### DEC-4 — `SuppressTokens` applied unconditionally — RISK

Python appends the filter only `if self.options.suppress_tokens:` — a falsy
value means no suppression at all. Rust always built and applied the mask
(`src/decoding.rs:335`), so the control-token set was suppressed even with
`suppress_tokens: None`, with no way to disable it. Arguably safer; not
parity.

**Fixed** in this change: the logic moved into a new `suppress_token_ids()`
function that returns `None` for `None`/`Some("")`, mirroring the `if
self.options.suppress_tokens:` guard, and `decode()` skips the filter entirely
when it returns `None`. Covered by the new fixture-driven test
`suppress_tokens_is_not_installed_for_a_falsy_option`.

### DEC-5 — `compression_ratio` uses a different deflate backend — RISK

`Cargo.toml` pulls `flate2` with default features, i.e. the **miniz_oxide** Rust
backend. Level (6) and container (zlib) match CPython, but the output is not
byte-identical, so compressed lengths differ by a few bytes and the ratio
shifts. `compression_ratio_threshold = 2.4` is a cliff, so borderline segments
can flip the temperature-fallback decision.

**Fix:** build `flate2` against C zlib (`features = ["zlib"]`).
**Test:** `src/decoding.rs::tests::compression_ratio_matches_cpython_zlib`
compares against values measured from CPython's `zlib`.

### DEC-6 — logits are never cast to f32 — RISK

Python's `Inference.logits` always casts decoder output back to `mx.float32`
before any filter or softmax. Rust has no cast, so with the fp16 weights that
mlx-community publishes, `softmax_axis` for `no_speech_prob`
(`src/decoding.rs:355`) runs in **fp16** where Python runs it in fp32. The
sampling path is promoted to f32 only incidentally, by adding the f32 masks.

### DEC-7 — `avg_logprob` on an empty token list — RISK

Python returns `sum_logprobs / 1` (a near-zero, i.e. *good* score); Rust used
to return `f32::NEG_INFINITY` (`src/decoding.rs:397-401`), which forced the
whole temperature-fallback ladder. Practically unreachable while
`suppress_blank` is on and timestamps are enabled. The `+1` divisor itself
matched.

**Fixed** in this change: the `NEG_INFINITY` special case is gone; the
expression is now `sum_logprobs / (len + 1)` unconditionally, exactly as
upstream.

### DEC-8 — `max_initial_timestamp: Some(0.0)` was treated as a hard cap of index 0 — **BUG**

Python guards with `if self.options.max_initial_timestamp:`, and `0.0` is
falsy in Python — so `max_initial_timestamp = 0.0` is documented shorthand for
*no cap at all*. The `max_ts_index` computation in `src/decoding.rs` instead
`.map()`ped `Some(0.0)` straight through to index `0`, inverting the intent:
every window's first sampled timestamp was pinned to exactly `<|0.00|>`.

**Fixed** in this change: `options.max_initial_timestamp.filter(|&t| t !=
0.0)` before the `.map(...)` (`src/decoding.rs:356-361`), so `Some(0.0)` now
behaves as "no cap", matching Python's falsy check. The mapped index is also
now clamped with `.max(0.0)`, since a negative value (nonsense either way)
would otherwise round to a negative-then-cast index.

### DOC-level gaps

`prefix` option absent (only `prompt` is supported); `best_of` / `n_group` /
`MaximumLikelihoodRanker` / `length_penalty` absent (single trajectory only —
note beam search is *not* a gap, upstream raises `NotImplementedError`);
`task="lang_id"` and `DecodingResult.language_probs` / `audio_features` absent;
`DecodingOptions.language` and `.task` are dead fields read nowhere in
`decoding.rs`; dead placeholder code in `select_next_token`
(`src/decoding.rs:194, 205-210`); `Tokenizer::decode` filters at `< eot` where
Python filters at `< timestamp_begin`.

**Verified matching:** `SuppressBlank` timing and mask contents; `no_timestamps`
suppression; both branches of the pairing rule and the
`last_was_timestamp`/`penultimate_was_timestamp` definitions; the
`len(tokens) == sample_begin` gate and the inclusive `max_initial_timestamp`
bound; `sample_begin`/`sot_index` bookkeeping with a prepended prompt;
`sample_len` default `n_text_ctx // 2`; `sum_logprobs` accumulated from
`log_softmax` of the **post-filter** logits; `no_speech_prob` taken from the
**first** forward pass pre-filter; the `+1` in `avg_logprob`;
`non_speech_tokens` construction.

## `whisper.rs` / `load_models.rs`

### MODEL-1 — quantized models are silently mis-loaded — **BUG**

Python (`load_models.py:36-41`) pops `quantization` and calls `nn.quantize(...)`
before `model.update`. Rust (`src/load_models.rs:308-311`) calls
`obj.remove("quantization")` and does nothing else. For any
`mlx-community/whisper-*-4bit` / `-8bit` repo the packed `uint32` `.weight` is
assigned straight into a dense `Linear` and `.scales`/`.biases` are dropped —
a shape/dtype failure in `matmul`, or garbage. No `QuantizedLinear` path exists.
Undocumented.

### MODEL-2 — example CLI panics on a value-less flag — **BUG**

`examples/transcribe.rs:50-53` did `{ i += 1; model_id = args[i].clone(); }`
with no bounds check, so `--model` as the last argument panicked with
`index out of bounds` instead of printing usage. Same for `--language`,
`--task`, `--assets`. **Fixed** in an earlier pass: `take_value` now goes
through `args.get(*i)` and returns `Err("{flag} requires a value")` instead of
indexing directly.

A second hole in the same `match` survived that fix: the catch-all arm matched
`s if !s.starts_with("--")`, so a mistyped short flag such as `-x` was
swallowed as the positional audio file, and the *real* file that followed it
then tripped the duplicate-file error above it. **Fixed** in this change: the
guard is now `!s.starts_with('-')`.

### MODEL-3 — no dtype/fp16 knob — RISK

Python takes `dtype: mx.Dtype` and `transcribe.py` passes `mx.float16` by
default. Rust has no dtype parameter anywhere; f32 positional embeddings and
f32 masks get added to fp16 activations, so mlx promotes the whole encoder and
decoder to f32. Numerically fine — arguably more accurate — but permanently
pinned to upstream's `--fp16 False` behaviour: roughly 2× slower and 2× memory
on Apple Silicon, with no way to opt out.

### MODEL-4 … MODEL-8 — RISK / DOC

* Encoder shape assert (`"incorrect audio shape"`) dropped; a wrong-sized mel
  yields an opaque mlx broadcast error.
* Weights are never force-evaluated at load (`mx.eval(model.parameters())`
  absent), so load stays lazy and decode failures surface mid-transcription.
* Unknown `config.json` keys are silently ignored where Python raises
  `TypeError`.
* `alignment_heads` is overridden from a weights key — a non-upstream addition.
* `num_languages()` returns `usize` and computes `n_vocab - 51765`, which
  panics in debug / wraps in release for `n_vocab < 51765`.
* `.npy` v2 headers are sliced two bytes early, `fortran_order` is unchecked,
  and a 10-byte file panics rather than erroring.
* The example CLI implements 5 flags against upstream's ~30; there is no
  `writers` module, so no srt/vtt/tsv/json output. Default model and default
  `verbose` also differ.

### MODEL-9 — example CLI passes a raw waveform to `detect_language` — **BUG**

`detect_language` accepts only a 2-D/3-D mel spectrogram, not a 1-D waveform.
`examples/transcribe.rs` called it with `audio` — the raw samples straight out
of `load_audio` — so the default invocation (multilingual model, no
`--language` flag) always failed with "mel must be 2-D or 3-D, got 1-D". Every
documented example command in this file's own `--help` text hits this path.

**Fixed** in this change: the example now computes
`log_mel_spectrogram(audio.clone(), model.dims.n_mels, &assets_dir,
N_SAMPLES)` first and passes the resulting mel, mirroring the padding
`transcribe` uses internally so the language-ID window matches what decoding
will see.

### Not a gap — sharded safetensors

Upstream `load_models.py:29-32` looks **only** for `weights.safetensors`,
falling back to `weights.npz`; it has no `model.safetensors.index.json`
handling either. `src/load_models.rs:165-176` mirrors this exactly, and
mlx-community whisper repos publish a single `weights.safetensors`. This is
**parity, not a Rust limitation**.

**Verified matching:** `ModelDimensions` field set and order; attention scale
`(n_state // n_head) ** -0.25` applied to *both* q and k; key projection
bias-free while q/v/out are biased; reshape/transpose axis orders;
`softmax(..., precise=True)`; self-attention KV concat on axis 1 and
cross-attention KV cached once and reused; pre-LN residual ordering; MLP
`n_state*4` with the exact erf GELU; `LayerNorm` eps `1e-5`; decoder positional
slice `[offset : offset+seq_len]`, final `ln`, and weight-tied output
projection; conv kernel/stride/padding under mlx's channels-last layout
(**no transpose is needed and none is done — correct**); `sinusoids` formula,
exponent sign, outer product and `[sin, cos]` concat order (no off-by-one).

## `transcribe.rs` / `tokenizer.rs`

### TR-1 — blank segments contaminate the prompt buffer and the final text — **BUG**

Python (`transcribe.py:507-514` → `524-530`) **clears** `tokens = []` on
instantaneous/blank segments *before* extending `all_tokens`, so their tokens
never enter the prompt-conditioning buffer nor the transcript. Rust
(`src/transcribe.rs:480-482` → `489-492`) extends `all_tokens` **first** and
filters afterwards.

Blank and zero-length segments therefore end up in
`all_tokens[prompt_reset_since..]`, which is fed as `<|startofprev|>` context
to every subsequent window, and in the final `text`. Errors compound across a
long file.

### TR-2 — `initial_prompt` is ignored when `condition_on_previous_text = false` — **BUG**

Upstream passes `decode_options["prompt"] = all_tokens[prompt_reset_since:]`
**unconditionally** (`transcribe.py:296`); the reset happens *after* the window
(`:532-534`). So with `condition_on_previous_text=False` the **first** window
still receives the initial-prompt tokens, because `prompt_reset_since` is still
0. Rust (`src/transcribe.rs:336-341`) passes `None` whenever
`condition_on_previous_text` is false, so `initial_prompt` — a documented
feature of this crate — is silently dropped in that mode.

### TR-3 — blank segments are dropped from output instead of cleared in place — RISK

Python (`transcribe.py:507-514`) keeps a blank/instantaneous segment: it clears
`text=""` and `tokens=[]` in place but leaves the segment (and its id) in
`all_segments`. Rust instead filtered such segments out of `current_segments`
entirely with `s.start < s.end && !s.text.is_empty()`, then renumbered every
remaining id sequentially. Segment ids and counts therefore diverged from the
reference on any file with a blank window, and `start < end` also dropped
`start > end` segments that Python keeps.

**Fixed** in this change: the loop now clears `text`/`tokens` in place on
`seg.start == seg.end || seg.text.trim().is_empty()` — upstream's own
condition — instead of filtering the vector, so nothing is ever dropped. The
now-redundant id-renumbering pass after the loop is gone: ids are assigned at
construction from `all_segments.len() + current_segments.len()` and stay
`0..n` in order on their own.

### TR-4 — segment text and the final aggregate text were trimmed — **BUG**

Rust `.trim()`ed each segment's `text` at construction and the final
aggregate `text` (`src/transcribe.rs:418, 456, 518` in the pre-fix layout);
upstream's `new_segment` and the final `tokenizer.decode(...)` never strip, so
every segment loses Whisper's conventional leading space (`" Hello."` vs
`"Hello."`) — byte-different from the reference on every run, though
semantically equivalent.

**Fixed** in this change: both `.trim()` calls are removed
(`src/transcribe.rs:442, 480, 546`). Note the `.trim()` in
`src/decoding.rs`'s `decode()` is a *different* call on a *different* value
(the raw decoded token text before segmentation) and is correct as-is —
openai's `decoding.py` does strip there. It stays.

### TR-5 — segment text tokens filtered at `timestamp_begin` instead of `eot` — **BUG**

The per-segment text-token filter in `src/transcribe.rs` used `t <
timestamp_begin` (50364), where upstream's `new_segment` uses `token <
tokenizer.eot` (50257). Special tokens in `[eot, timestamp_begin)` — language
ids, `<|notimestamps|>` — were therefore decoded straight into the segment
text as literal `<|xx|>` instead of being dropped. This is the mirror image of
the pre-existing, still-open `Tokenizer::decode` gap noted above: that one
strips too much (`< eot` where Python wants `< timestamp_begin`), this one
kept too much (`< timestamp_begin` where Python wants `< eot`).

**Fixed** in this change: both call sites now filter with `t <
tokenizer.eot()` (`src/transcribe.rs:430, 473`).

### TR-6 — `initial_prompt` was re-encoded after the decode loop — **BUG**

To recover how many tokens of `all_tokens` were the initial prompt (so the
final text excludes them), `src/transcribe.rs` re-ran
`tokenizer.encode(&format!(" {}", ...))` on the prompt a second time after the
loop. BPE encoding is not guaranteed idempotent-by-construction across two
independent calls in the way this relied on, and the recomputation was pure
waste on every run regardless.

**Fixed** in this change: the length is recorded once, in
`initial_prompt_len`, right where the prompt is first encoded before the loop
(`src/transcribe.rs:321-325`), and reused at the end (`:546`).

### TR-7 — timestamp offsets were clamped at zero — **BUG**

The per-segment offsets were computed with `u32::saturating_sub`:

```rust
let start_ts = sliced[0].saturating_sub(ts_begin) as f32;
```

Upstream subtracts plain Python integers
(`sliced_tokens[0].item() - tokenizer.timestamp_begin`), so a slice that does
not open on a timestamp token yields a **negative** offset and a segment that
starts before the window does. Rust clamped that to `0`, silently moving the
segment boundary. Every slice reachable today opens on a timestamp — the slice
boundaries come from `consecutive`, which indexes timestamp pairs — so this was
latent rather than live, but it is the kind of guard that turns a future
divergence into a wrong answer instead of a visible one.

**Fixed** in this change: the offsets are computed as `i64` and kept signed
(`src/transcribe.rs`, `split_window`). The seek-advance arithmetic is left
unsigned deliberately: `tokens[last_slice - 1]` is provably a timestamp there,
and a hypothetical negative flowing into a `usize` frame count would be worse
than the clamp. Pinned by `split_window_keeps_a_negative_start_offset` against
the `negative_start_offset` fixture case.

### TOK-1 — language index is searched against the untruncated table — **BUG**

Upstream truncates first: `langs = tuple(LANGUAGES.keys())[:num_languages]`,
then `sot + 1 + langs.index(language)`, raising `ValueError` outside the window.
`src/tokenizer.rs:224-225` searches the full 100-entry `LANGUAGES` and swallows
misses with `unwrap_or(0)`.

Concretely: `yue` is table index 99, so for a 99-language model the port emits
`50258 + 1 + 99 = 50358` — which is `<|translate|>`. A task token silently
stands in for a language token. Any unrecognised future code collapses to
English instead of erroring.

**Test:** `tests/tokenizer_parity.rs::language_outside_num_languages_window_is_rejected`,
`::every_language_code_maps_to_its_positional_token`.

### TOK-3 — `all_language_tokens` ordering is non-deterministic upstream — RISK (measured)

`tokenizer.py:145` builds `special_tokens` by iterating
`self.encoding.special_tokens_set` — a Python **set** — so
`all_language_tokens` comes back in an order that changes with
`PYTHONHASHSEED`. Measured across three seeds:

```
seed=1 first8: [50308, 50273, 50270, 50263, 50327, 50292, 50280, 50306]
seed=2 first8: [50290, 50293, 50259, 50269, 50308, 50276, 50357, 50264]
seed=3 first8: [50300, 50301, 50326, 50277, 50316, 50271, 50332, 50350]
```

The sorted set and the token→code pairing *are* stable across seeds (verified),
and `all_language_codes` is derived from `all_language_tokens` by decoding, so
`detect_language` stays correct despite the shuffle. It does mean the
`[: self.num_languages]` truncation would drop an arbitrary language if the
vocabulary ever carried more language tokens than `num_languages`.

This port returns them in `LANGUAGES` order — deterministic, and a superset of
what upstream actually guarantees. The tests assert the set and the pairing
rather than the order, since pinning the order would bake one arbitrary run of
the fixture generator into the suite.

### TOK-2 — the BPE encoder skips tiktoken's pre-tokenization — RISK (measured)

`tokenizer.py:363` applies tiktoken's `pat_str` regex before BPE; Rust
(`src/tokenizer.rs:157-196`) runs BPE straight over raw bytes. Measured against
the real `multilingual.tiktoken`: divergence on ~1.7% of random ASCII strings,
systematically on uppercase apostrophe forms.

```
" DON'T STOP"  tiktoken -> [' DON', "'", 'T', ' STOP']
               this port -> [' DON', "'T", ' STOP']
```

The only text→token path reachable today is `initial_prompt`, so this perturbs
prompt conditioning rather than decoding. It is also O(n²·V) per call.
`non_speech_tokens` was verified **identical** (82 ids) despite this.

**Test:** the fixture `encode_decode` set now includes `" DON'T STOP"`,
`" IT'S A TEST"` and `" ALL CAPS SENTENCE WITH THE'S"` alongside controls that
must keep passing.

**Residual gap, now fixed:** even with `pat_str` applied, the character
classes it keys on, `\p{L}` and `\p{N}`, were approximated by
`char::is_alphabetic` / `char::is_numeric` — the derived Unicode
`Alphabetic`/`Numeric` properties, wider than the raw general categories
(`Alphabetic` also covers `Nl` and `Other_Alphabetic`, the latter including
Indic combining vowel signs such as U+093F). `src/tokenizer.rs` now tests the
raw general categories directly, via the new `unicode-general-category`
dependency, instead of the derived properties. New unit tests
(`combining_marks_are_not_letters`, `letter_numbers_are_numbers`) cover the
Devanagari and `Nl` cases respectively.

### Remaining transcribe/tokenizer RISKs — TOK-4 and unnumbered

* **`encode()` accepts special-token text.** Rust injects special-token bytes
  into the encoder, so a literal `<|endoftext|>` in an `initial_prompt` is
  tokenized instead of raising as tiktoken does — a control-token injection
  path.
* **`Tokenizer::decode` filters at `< eot`** where Python filters at
  `< timestamp_begin`, so Rust strips ids in `[eot, timestamp_begin)` that
  Python renders literally.
* **`detect_language` mel padding.** Python pads the *audio* with 30 s of
  silence before the mel, so short clips see mel-of-silence (a nonzero constant
  after normalisation); Rust pads with `0.0` in mel space. Language ID gets
  numerically different input for any clip under 30 s. Same root cause as
  `AUDIO-2`.
* **Anti-stall seek guard.** When the last consumed timestamp is `<|0.00|>`
  upstream does `seek += 0` and spins forever; Rust jumps a full 30 s window
  (`src/transcribe.rs:437, 497-499`). A defensive addition that silently drops
  that window's audio where upstream hangs.
* **Silence-skip boundary.** Python skips when `avg_logprob <= threshold`,
  Rust when `< threshold` — differs only at exact float equality.
* **Timestamp arithmetic in f32.** `time_offset + ts_pos * time_precision` uses
  `f32` where Python uses `f64`; 0.02 s granularity at 8.3 h needs ~7
  significant digits, so long-file boundaries can round differently.
* **`split_tokens_on_spaces` punctuation test** differs on the empty subword —
  dead code, only the absent word-timestamp path calls it.

### DOC / OK-DIFF

Leftover `// ADDED FOR DEBUGGING` output in `src/transcribe.rs:357-361`;
`verbose` is `bool` where Python's is tri-state `Optional[bool]`
(None/False/True → silent / progress bar / text). Omitted upstream features:
word timestamps and DTW, hallucination-silence VAD, `clip_timestamps`,
`prefix`, beam/best-of knobs — all default to off upstream, so the default path
is unaffected.

**Verified matching:** `LANGUAGES` — **100 entries on both sides, same order**
(`yue` last); the full special-token id layout (`endoftext`=50257, `sot`=50258,
languages 50259-50357, `translate`=50358, `transcribe`=50359, `startoflm`=50360,
`startofprev`=50361, `nospeech`=50362, `notimestamps`=50363,
`timestamp_begin`=50364) and Rust's positional `add_special` ordering;
`n_vocab` computation; `non_speech_tokens` — **82 identical ids**, symbol string
and miscellaneous set char-for-char equal including the `" -"` / `" '"` seeding;
`sot_sequence` for en/transcribe; prompt truncation to `n_text_ctx/2 - 1`
keeping the tail; the `detect_language` masking path; default temperatures,
thresholds and `max_initial_timestamp`; `input_stride` / `time_precision` /
`time_offset` formulas; `single_timestamp_ending` and consecutive-pair
detection; the seek-advance branch selection; `prompt_reset_since` on
`temperature > 0.5`; the `decode_with_fallback` no-speech override ordering.
**Rust hardcodes no token ids** — all are derived positionally.

### Not covered by CI

The **GPU path**. `MLX_WHISPER_RS_TEST_CPU` pins MLX to the CPU device because
GitHub's macOS runners are VMs with paravirtualised Metal, where GPU work
aborts (`AppleParavirtCommandBuffer` assertion → SIGABRT, which killed the
whole test binary). Everything numeric here is device-independent, but a real
Mac is still needed to exercise Metal.

Also uncovered: anything requiring **model weights** — the encoder/decoder
forward passes and real end-to-end transcription. A golden test against
Python-mlx logits for `whisper-tiny` would close that gap.

Two pieces that used to sit behind that wall no longer do. The `transcribe`
seek loop's arithmetic — window splitting, seek advance, the silence skip and
the temperature-fallback gate — was lifted into free functions over plain
numbers (`split_window`, `should_skip_window`, `needs_fallback`, `text_tokens`
in `src/transcribe.rs`) and is pinned against
`tests/fixtures/segmentation.json`. And the decoder's KV-cache offset
arithmetic is covered by `tests/decoder_cache.rs`, which asserts that a
full-sequence forward pass equals token-by-token cached decoding on a
randomly-initialised tiny model — an invariant that holds for any weights, so
it needs no download. What is still model-only is the surrounding orchestration:
the prompt buffer, `prompt_reset_since`, blank-segment clearing, and the
encoder/decoder numerics themselves.

## Suggested order of work

Everything on the original ten-item list has shipped, across the initial
audit-fix commit and the code-review pass above (`DEC-2` was a decision, now
pinned by fixture, not a fix). What is left is what the findings above still
mark RISK or DOC and leave open:

1. `DEC-6` — cast decoder logits to f32 before any filter or softmax, matching
   `Inference.logits`'s unconditional cast, so fp16 weights don't run
   `no_speech_prob`'s softmax in fp16.
2. Real quantized-model support (`MODEL-1` beyond its current rejection) —
   `QuantizedLinear` / `QuantizedEmbedding`, or leave the explicit error as the
   permanent answer.
3. `MODEL-3` (no fp16/dtype knob) — declined for now; revisit only if the 2×
   memory/speed cost on Apple Silicon becomes a real complaint.
4. `AUDIO-5`, `AUDIO-6`, `AUDIO-7`, `AUDIO-8` — harden the `.npy` reader and
   WAV parser (header validation, `EXTENSIBLE`/24-bit formats, sample-rate
   enforcement, the `stft` frame-count underflow).
5. The remaining `transcribe.rs`/`tokenizer.rs` items — `encode()` accepting
   special-token text, `Tokenizer::decode`'s `< eot` vs `< timestamp_begin`
   mismatch, `detect_language`'s mel-padding gap (same root cause as the
   already-fixed `AUDIO-2`), the anti-stall seek guard, the silence-skip
   boundary, `f32` timestamp arithmetic, `split_tokens_on_spaces`, and
   `TOK-3`'s non-deterministic upstream ordering.
6. A golden test against Python-mlx logits for `whisper-tiny` — the only way
   to cover the encoder/decoder forward passes and the `transcribe` seek loop,
   none of which any current test exercises.
7. GPU coverage on a real Mac — CI only exercises the CPU device
   (`MLX_WHISPER_RS_TEST_CPU`).
